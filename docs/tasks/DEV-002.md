# DEV-002 Capture と Replay 互換性の技術検証

Status: Ready for review
Owner: orchestrator
Phase: P1  
Product relation: TRACE-CAP-001, TRACE-CAP-002, TRACE-DECODE-001, REPLAY-EDIT-001

## 目的

DEV-001 の proxy chain を維持したまま、後の検索、編集、意味的 replay に必要な request 情報を保存し、プロセス再起動後に読み戻せることを証明する。完成 UI や本番用 storage は作らず、記録契約と技術経路を確定する。

- `/AGENTS.md`
- `/docs/development/WORKFLOW.md`
- `/docs/architecture/CAPTURE_CONTRACT.md`
- `/docs/reviews/DEV-001-review-001.md`
- この文書

過去の会話は不要である。

## スコープ

含む:

- inspector から request record を生成する capture addon または同等機構
- runtime record を Git 管理外へ保存
- capture schema version
- raw path/query、ordered headers、raw body bytes、body metadata、capture status
- 保存後の inspector/reader 再起動と読み戻し
- 保存済み request の意味的 replay
- query または form の一項目を変更した replay
- JSON、URL-encoded form、multipart、binary body の検証
- 重複 query と重複可能 header の保持検証
- 大容量 upload の転送継続と capture limit 状態
- WebSocket handshake の pass-through と metadata 記録
- 自動 black-box test と検証文書

含まない:

- 管理 UI
- 長期運用 DB の確定
- 20 GB retention cleanup
- Docker discovery
- 自動 request rewrite rule
- live intercept
- response body の完全保存
- 認証、権限分離、機密情報 filter、公開環境 hardening

## 記録の最低条件

記録は `/docs/architecture/CAPTURE_CONTRACT.md` に従う。特に次を禁止する。

- query/header を単一値 map に潰す
- binary body を UTF-8 text のみに変換する
- decoded path だけを保存する
- truncated/metadata-only record を replayable と扱う

## 受入条件

1. DEV-001 の全 routing test が引き続き成功する。
2. GET、JSON POST、URL-encoded form、multipart、binary body の record が保存される。
3. `tag=first&tag=second` のような重複 query が順序付きで保持される。
4. raw body bytes の size と SHA-256 が送信内容と一致する。
5. inspector または reader の再起動後に既存 record を読み戻せる。
6. 完全 record 一件を replay し、Echo target で method/path/query/body の意味的一致を確認できる。
7. 保存済み record の query または URL-encoded form 一項目を変更して replay し、変更後の値だけが target に届く。
8. 100 MiB upload が target まで完了し、capture 上限を超えた場合は `truncated` または `metadata-only` として non-replayable になる。メモリ量の厳密 benchmark は本 task の範囲外とする。
9. WebSocket 接続を破壊せず、handshake metadata を記録する。frame 保存/replay は不要。
10. capture parse failure が proxy routing を停止させない。
11. 一つの自動 test command で上記を再現できる。

## 失敗時の扱い

- mitmproxy native flow だけでは contract を安定して出力できない場合、addon で project-owned record を生成する。
- body capture が大容量転送を壊す場合、capture limit を導入し、上限超過を non-replayable として明示する。
- 二つの記録方法を試しても小さな request の raw bytes、重複値、再起動後読み戻しを同時に満たせない場合は `Blocked` とする。
- security hardening を理由に task を停止しない。

## 実装 Agent 記入欄

### 実装要約

- **Capture Addon (`services/recorder/addon.py`, `services/recorder/parser.py`)**:
  - `CAPTURE_CONTRACT.md` (`schema_version: "v0"`) に従い、`inspector` (mitmproxy) でリクエストの原始情報（`method`, `scheme`, `authority`, `raw_target`, `raw_path`, `raw_query`, `http_version`, 順序付き重複可能 `headers`/`trailers`）を `captures/<capture_id>.json` に、原始 body bytes を `blobs/<capture_id>.bin` に分離保存する構成を実装した。
  - 派生ビュー（`query_params`, `cookies_view`, `json_view`, `form_view`, `multipart_view`, `text_preview`, `hex_preview`, `parse_errors`）は `parser.py` で生成し、不正 JSON や不正 multipart の解析失敗時は `parse_errors` にエラーを記録してプロキシ転送および原始 bytes の `complete` 保存を継続する。
  - `CAPTURE_MAX_BODY_BYTES`（既定 1 MiB）を超える大容量リクエストは `requestheaders` フックで `flow.request.stream` によるストリーミング転送に切り替え、100 MiB アップロードもメモリ肥大化なく target まで完走させつつ全体サイズと SHA-256 を記録し、`capture_status: "truncated"` / `replayable: false` として保存する。
  - WebSocket Upgrade (`101 Switching Protocols`) は接続を破壊せず双方向フレーム通信を通過させ、ハンドシェイク情報を `is_websocket: true` / `capture_status: "metadata-only"` / `replayable: false` として記録する。
- **Reader / Semantic Replay CLI (`services/recorder/capture_cli.py`, `scripts/capture-ctl.sh`)**:
  - `list` / `get`: 保存済みレコードと blob の読み戻し、SHA-256 整合性検証、および原始データからの派生ビュー再生成を行う。
  - `replay`: `replayable: true` (`capture_status == "complete"`) のレコードのみを許可し、hop-by-hop ヘッダー（`Host`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Proxy-Connection`, `Keep-Alive`）を再構築して `edge` へ再送する。`--set-query KEY=VALUE` および `--set-form KEY=VALUE` により単一項目のみを変更した意味的リプレイをサポートし、`truncated` / `metadata-only` / WebSocket レコードのリプレイは拒否（exit code 2）する。
- **Nginx / Echo Target 拡張 (`deploy/nginx/edge/default.conf`, `deploy/nginx/router/default.conf`, `tests/helpers/echo_server.py`)**:
  - `client_max_body_size 0;` / `proxy_request_buffering off;` および WebSocket `Upgrade` / `Connection` ヘッダー透過を追加した。
  - `echo_server.py` にチャンクストリーム読み取りによる大容量 `body_size` / `body_sha256` 計測と RFC 6455 WebSocket ハンドシェイク・フレームエコーを追加した。

### 実行した検証

以下の単一コマンド列でクリーン状態からの起動、DEV-001 回帰テスト、DEV-002 全受入条件の統合テスト、停止・クリーンアップを実行し、すべて成功することを確認した。

```bash
make clean && make test && make down
```

（`make test` は `./tests/integration/test_proxy_chain.sh` と `./tests/integration/test_capture_replay.sh` を連続実行）

検証結果の要約:

1. **AC-1 (DEV-001 回帰テスト)**:
   - `./tests/integration/test_proxy_chain.sh` 全 9 ステップが成功 (`PASS`)。
2. **AC-2 / AC-3 / AC-4 (5 種類のリクエスト保存・重複クエリ/ヘッダー順序・SHA-256 一致)**:
   - GET（`%2F` を含む raw_path、重複 query `tag=first&tag=second`、重複 header `X-Custom-Multi`）、JSON POST、URL-encoded form POST、multipart POST（テキスト項目＋バイナリファイル項目）、raw binary POST（0x00..0xFF を含む 512 bytes）を送信し、全レコードの `size` と `sha256` が送信内容と完全一致することを確認 (`PASS`)。
3. **AC-5 (再起動後の読み戻し)**:
   - `docker compose restart inspector` 実行後、コンテナ内 reader およびホスト側 reader (`capture_cli.py --storage-dir var get <id>`) の双方から全 5 種類のレコードと blob を読み戻し、SHA-256 検証および派生ビュー再生成が一致することを確認 (`PASS`)。
4. **AC-6 (完全レコードの意味的リプレイ)**:
   - 保存済み JSON POST および Binary POST レコードを `capture-ctl.sh replay <id>` でリプレイし、Echo target で `method`, `path`, `raw_query`, `body_size`, `body_sha256`, `body_json` が一致することを確認 (`PASS`)。
5. **AC-7 (query / form 一項目変更リプレイ)**:
   - GET レコードに対する `--set-query filter=archived` リプレイで、`tag=first&tag=second&empty=` を保持したまま `filter` のみが `archived` に変更されて target に届くことを確認 (`PASS`)。
   - URL-encoded form レコードに対する `--set-form role=admin` リプレイで、`action=update` と `flag=one&flag=two` を保持したまま `role` のみが `admin` に変更されて target に届くことを確認 (`PASS`)。
6. **AC-8 (100 MiB アップロード転送継続と capture limit)**:
   - `104,857,600` bytes (100 MiB) のバイナリ POST が `echo-a` まで完走し、target 側の `body_size` (`104857600`) と `body_sha256` が送信元と完全一致することを確認 (`PASS`)。
   - 記録は `capture_status: "truncated"`, `captured_size: 1048576` (1 MiB), `replayable: false` となり、`replay` 実行時に `non_replayable_capture` として拒否されることを確認 (`PASS`)。
7. **AC-9 (WebSocket 通過と handshake metadata 記録)**:
   - `GET /ws/live?room=alpha&mode=realtime` の WebSocket Upgrade (`101 Switching Protocols`) とマスク付きテキストフレーム `"hello-websocket"` の双方向送受信が成功し、レコードに `is_websocket: true`, `capture_status: "metadata-only"`, `replayable: false`, `websocket_handshake` メタデータが保存されることを確認 (`PASS`)。
8. **AC-10 (capture parse failure 耐性)**:
   - 不正 JSON (`{"unterminated": [1, 2, `) および boundary 不整合の不正 multipart リクエストを送信し、いずれもプロキシ転送は停止せず HTTP `200` で target に到達し、原始 bytes は `complete` で保存され `derived_views.parse_errors` にエラーが記録されることを確認 (`PASS`)。

### 未検証事項

- メモリ使用量の厳密なベンチマーク計測（タスク定義に従い範囲外）。
- WebSocket 個別フレーム単位の保存・リプレイ（タスク定義に従い範囲外）。
- 20 GB ストレージ上限到達時の自動ローテーション（後続フェーズ対象）。

### 発見事項

- `mitmproxy/mitmproxy` 公式イメージは起動時に `gosu mitmproxy` で一般ユーザーへ降格するため、Docker named volume のマウントポイント (`/var/lib/proxyconsole`) を `services/recorder/Dockerfile` 内で事前に作成・権限付与しておくことで権限エラーを防止した。
- 大容量リクエスト（100 MiB）では `requestheaders` フックで `flow.request.stream` にチャンクコールバックを設定することで、mitmproxy 内での全文メモリバッファリングを回避しつつ全体サイズと SHA-256 の正確な算出および先頭 `CAPTURE_MAX_BODY_BYTES` の切り詰め保存を両立できた。
