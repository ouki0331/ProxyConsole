# DEV-020 Route 管理 core と原子的 Nginx 反映

Status: In progress
Owner: implementer
Phase: P3  
Product relation: ROUTE-HOST-001, ROUTE-HOST-002, ROUTE-HOST-003, ROUTE-HOST-004, ROUTE-CFG-001

## 目的

手動編集なしで domain route を作成、複製、変更、有効化・無効化し、検証済み Nginx 設定へ原子的に反映できる control plane core を実装する。Docker discovery と Web UI は後続 task に分離する。

## スコープ

含む:

- route 永続 model と migration
- route list/get/create/update/delete
- route copy/clone
- enable/disable
- domain/host、upstream scheme、host、port の手動指定
- 複数 domain が同じ upstream を共有する構成
- route validation と重複 domain 検出
- Nginx router config 生成
- `nginx -t` 後の原子的反映と reload
- 反映失敗時の旧設定維持/rollback
- route apply status と最後の失敗理由
- local HTTP API と CLI
- 自動 integration test

含まない:

- Docker container discovery（DEV-021）
- Web 管理 UI（DEV-022）
- 証明書自動発行
- capture viewer/replay editor
- security hardening、認証、権限分離

## 機能ルール

1. 一つの有効 domain は一つの route だけに属する。
2. 複数 route/domain は同じ upstream host/port を参照できる。
3. 無効 route は設定として保持するが、Nginx へ有効 route として反映しない。
4. copy は新しい route ID を作成し、domain は明示的に変更されるまで conflict 状態として保存せず、作成時に新 domain を必須とする。
5. create/update/delete/enable/disable は desired state 保存と apply result を区別する。
6. 新設定の `nginx -t` が失敗した場合、現在稼働中の設定を変更しない。
7. reload failure 後も旧 route が継続して応答する。

## 受入条件

1. DEV-001〜DEV-011 の全 test が引き続き成功する。
2. API/CLI で手動 upstream route を create/list/get/update/delete できる。
3. route を copy し、新 domain だけ変更して同一 upstream へ転送できる。
4. 異なる複数 domain が同じ upstream へ正しく転送される。
5. enable/disable が live routing に反映され、disabled domain は unknown route になる。
6. duplicate domain、無効 scheme、無効 port、空 host を拒否する。
7. create/update/delete 後、Nginx config が生成され `nginx -t` 成功後に reload される。
8. 故意に不正な生成候補を与えた場合、apply は失敗し、既存 route の応答が継続する。
9. control service/container restart 後も route desired state と最後の apply status が保持される。
10. route config file の一部書き込み状態が Nginx から観測されない。
11. route 変更が inspector/capture/index/retention chain を迂回しない。
12. 一つの自動 test command で全ルールを再現できる。

## 実装上の既定

- 現在の固定 app-a/app-b route は migration/seed として扱い、動的管理へ移行しても DEV-001 regression を維持する。
- Nginx config apply は temporary candidate、validation、atomic replace、reload の順に行う。
- UI 固有の都合を core model/API に混ぜない。
- route apply が失敗しても capture/search/retention API を停止しない。

## 失敗時の扱い

- 一件の不正 route により既存 route が停止する場合は `Blocked` とし、P3 を進めない。
- rollback/旧設定維持を証明できない場合は `Ready for review` にしない。
- security hardening を理由に task を停止しない。
