# DEV-050 Company-environment readiness assessment

Status: Deferred
Owner: none
Phase: P6
Product relation: OPS-BOUNDARY-001, DATA-RISK-001, DEPLOY-READINESS-001

> 2026-11-15 scope decision: 成果物と検証証拠は保持するが、製品を単一利用者・localhost 専用へ固定したため独立 review と G6 判定を延期する。会社共有、multi-user、SSO、RBAC、public deployment の follow-up を自動派生させない。ローカル runbook / backup evidence は将来必要時の参考資料として残す。

## 目的

完成した localhost 版 ProxyConsole を会社環境候補として評価するため、現状の trust boundary、保存データ、listen port、証明書、Docker socket、依存関係、容量、backup / restore、監査可能性を実証ベースで整理し、「そのまま利用可能」「設定で対応可能」「コード変更が必要」「会社判断が必要」を区別する。会社環境へ自動展開せず、公開化や認証方式を独断で決めない。

## スコープ

含む:

- container / network / host port / localhost management boundary の inventory
- HTTP capture、headers、body、replay draft、rule、route、notification、certificate key の data inventory
- Docker socket mount と実際に使用する Docker API operation の inventory
- certificate generation / storage / replacement / expiry の現状確認
- dependency / image / license / version pinning の inventory
- capture retention、notification growth、disk exhaustion behavior の確認
- configuration / SQLite / captures / blobs / certificates の backup / restore 検証
- log / incident / capture による運用監査可能性の確認
- WSL / Docker Desktop での再現可能な readiness check command
- company policy へ確認すべき decision list と、機能を壊さない hardening 順序

含まない:

- 会社環境への deployment
- 公開インターネットへの管理画面公開
- 認証方式、SSO、RBAC の独断実装
- raw capture を不可逆に削除・マスクする仕様変更
- certificate authority、secret manager、external backup service の選定
- 実在する会社データ・認証情報・秘密鍵の収集

## 機能ルール

1. assessment は実コード、Compose、runtime command、generated artifact に基づき、推測を confirmed fact として記載しない。
2. secret の有無を確認しても値を出力・commit しない。synthetic test data のみ使用する。
3. localhost-only 前提と、外部公開時に追加で必要な制御を分離する。
4. capture fidelity と secret masking / irreversible deletion を混同しない。候補は保存時除外、表示時 masking、選択削除を分けて評価する。
5. Docker socket は現在必要な read operation と write / lifecycle operation を区別する。
6. backup / restore は archive 作成だけで完了とせず、隔離した synthetic dataset を復元して route / capture / draft / rule / notification を読み戻す。
7. 既存 P1〜P5 機能を変更する必要がある場合、assessment では具体的な後続 task と acceptance を提案し、無断実装しない。
8. company policy が不明な項目は blocking decision として明示するが、プロジェクト全体を失敗扱いにしない。

## 受入条件

1. DEV-001〜DEV-042 の全 test が引き続き成功する。
2. host に公開される port、bind address、container network、Docker socket、volume mount を機械的に一覧化できる。
3. management API / console が既定で localhost boundary に留まることを runtime で確認し、外部 bind 時の影響を明記する。
4. 保存データ種別ごとに location、format、retention、機密性、backup 対象、削除方法を表にする。
5. certificate / private key の生成場所、権限、Git除外、交換手順、期限確認方法を記録する。
6. Docker socket に対して現在使用する API endpoint / operation と必要権限をコードから列挙する。
7. direct / transitive dependency、base image、ライセンス、version pinning の現状を再現可能な command で出力する。取得不能項目は理由を記録する。
8. disk usage と retention hard limit、notification / SQLite growth、disk-full 時の影響と回復手順を確認する。
9. synthetic data を使った backup / restore test で route、capture、draft、rule、notification の読み戻しを証明する。
10. ローカル運用 runbook に startup、health、config test、backup、restore、cleanup、certificate replacement、incident確認を含める。
11. readiness matrix で各項目を `ready` / `config_required` / `code_change_required` / `company_decision_required` に分類し、証拠と推奨後続 task を紐付ける。
12. assessment command と生成文書が secret、private key、runtime capture body を Git に追加しない。

## 失敗時の扱い

- 実在会社データ、会社ポリシー、CA、SSO、secret manager が必要な項目は `company_decision_required` とし、利用者判断を待つ。
- backup restore で synthetic data を読み戻せない場合は blocking finding とし、G6 を通過させない。
- localhost boundary が既定で成立しない場合は blocking finding とし、後続修正 task を作る。
- security finding を理由に既存ローカル版を削除・停止しない。

## 実装 Agent 記入欄

### 評価要約

1. **成果物の作成**:
   - `docs/operations/COMPANY_READINESS.md`: 現状の localhost 版 ProxyConsole (`P1`〜`P5` 完了状態) について、実コード・Compose 定義・runtime 検査・機械的検証に基づく会社環境準備評価レポートを作成した。
   - `docs/operations/LOCAL_RUNBOOK.md`: ローカル運用手順書（起動/停止、ヘルスチェック、設定検証、一貫性のあるオンラインバックアップ、完全破棄からのリストア、ストレージクリーンアップ、証明書確認・入替・ローテーション、インシデント/ログ調査、Readiness セルフチェック）を作成した。
   - `scripts/check-company-readiness.sh` (`make readiness-check`): 全7フェーズ（1: クリーン起動、2: ポート/ネットワーク/マウント/Docker API 使用状況の機械的検査、3: 証明書・秘密鍵の権限/Git除外/SAN/有効期限確認、4: ベースイメージ digest および全46パッケージ・ライセンスの出力、5: 合成データの投入と `sqlite3.Connection.backup()` を用いたオンラインバックアップ作成、6: 全ボリューム破棄後のリストア・再起動・全リソース読み戻しと実トラフィック疎通確認、7: ストレージ書き込み不能時のプロキシ継続性・インシデント通知・回復確認）を自動実行する検証スクリプトを実装した。
2. **主要な実証結果**:
   - **ネットワーク・境界**: 管理画面/API (`control-api`) は `127.0.0.1:18480->18480/tcp` のみにバインドされ、内部コンテナ群 (`inspector`, `router`, `echo-a`, `echo-b`) はホスト公開ポート `0`、内部ネットワーク `inspector_router_net` / `router_targets_net` はともに `internal: true` で外部から隔離されていることを runtime で確認した。
   - **データ・機密性・Retention**: 全10種類の保存データについて、保存パス、形式、保持期間、機密性、バックアップ対象、削除方法を一覧化した。Capture fidelity を維持するため不可逆な削除やマスクは行わず、候補となる3方式（保存時除外、表示時マスク、選択削除）を分離して評価した。
   - **証明書と秘密鍵**: `var/certificates/edge.key` (`0600`) / `edge.crt` (`0644`) は `.gitignore` により Git 追跡対象外であることを確認した。一方、`deploy/nginx/edge/Dockerfile` がビルド時に `var/certificates/` をイメージレイヤへ `COPY` しているため、ローカル利用では問題ないものの外部レジストリへ push する運用では秘密鍵混入リスクがあることを特定し、`code_change_required` (`DEV-051`: read-only bind mount 化) として分類した。
   - **Docker socket 最小権限**: `services/recorder/docker_discovery.py` の AST/正規表現スキャンにより、使用している Docker Engine API は `GET /containers/json?all=1` と `GET /containers/{id}/json` の2つの読み取り操作のみであり、書き込み・ライフサイクル操作は一切存在しないことを証明した。共有環境向けにソケットプロキシ導入または `chmod 0666` 廃止を `DEV-052` として整理した。
   - **バックアップ・リストア証明**: 合成データ（Route `route:readiness-app`、Rule `rule:readiness-header`、HTTPS Capture + バイナリ Blob、Draft + Replay 履歴、Notification + Ack、Retention Policy `min_retention_seconds=43200`）を作成してオンラインバックアップを取得し、`down.sh` でボリュームを完全破棄した後にリストアして全データが欠損なく読み戻せ、リストア後のルート・ルールが実トラフィックに即座に適用されることを実証した。
   - **Disk-full / 書き込み障害時の耐障害性**: `captures` / `blobs` ディレクトリを読み取り専用 (`0555`) にした疑似 Disk-full 状態でも、`edge -> inspector -> router -> echo-a` のプロキシ通信は HTTP `200` で継続し、`capture_write_failed` インシデント通知が記録され、権限回復後に再び `X-Capture-Status: complete` でキャプチャ保存が復旧することを実証した。

### 実行した検証

- `./scripts/check-company-readiness.sh` (`make readiness-check`) — Phase 1〜7 すべて PASS
- `make clean && make config-test && make test && ./scripts/check-company-readiness.sh && make down && make up` — `DEV-001`〜`DEV-042` の全12統合テストスイートおよび Readiness チェックがすべて PASS し、ローカルスタックが正常稼働中であることを確認
- `git status --short` および `git check-ignore -v var/certificates/edge.key var/certificates/edge.crt var/captures var/blobs var/database` — 秘密鍵・証明書・ランタイムデータが Git に一切含まれないことを確認

### 未確認事項

以下の項目は会社固有のセキュリティ・運用ポリシー判断 (`company_decision_required`) が必要なため、独断での実装や決定を行わず `docs/operations/COMPANY_READINESS.md` Section 10 に判断リストとして明記した：
1. **利用形態の範囲**: 個々の開発者端末上の localhost ツールとしてのみ利用するか、共有ステージング/社内サーバ上で複数人がアクセスする形態とするか。
2. **認証・認可 (SSO / RBAC) 要件**: 共有環境へ展開する場合の認証方式（OIDC/SAML リバースプロキシ、mTLS、API トークン等）と権限分離要件。
3. **証明書発行主体 (CA)**: 社内プライベート CA / ACME による証明書発行基準と、開発者端末への信頼ルート配布ポリシー。
4. **キャプチャデータ保護方針**: 生キャプチャに含まれる `Authorization` / `Cookie` / 個人情報等に対するポリシー（表示時マスク、特定ヘッダ/パスの保存時除外、選択パージ API、保持上限時間）。
5. **サプライチェーン・ライセンス承認**: `mitmproxy` (GPLv3) を含むコンテナイメージおよびベースイメージの社内利用・社内ミラーレジストリ要件。

### 推奨後続 task

既存 P1〜P5 の機能を一切壊さずに段階的ハードニングを行う場合の推奨タスク順序（詳細は `docs/operations/COMPANY_READINESS.md` Section 11 参照）：
- **DEV-051**: Edge TLS 証明書の Runtime Bind Mount 化（`deploy/nginx/edge/Dockerfile` から `COPY var/certificates/` を除去し、`docker-compose.yml` の read-only volume mount に変更）
- **DEV-052**: Docker Socket Read-Only Proxy 導入とホストソケット `chmod 0666` の廃止
- **DEV-053**: コンテナ Base Image Digest 固定と Python 依存パッケージの Hash Pinning (`requirements.lock`)
- **DEV-054**: キャプチャ機密ヘッダ表示マスク / 選択的保存除外・パージ機能（会社データ保護ポリシー確定後）
- **DEV-055**: 管理 API / Console 向け認証ゲートウェイ統合および変更監査ログ出力（共有環境公開判断後）
