# DEV-050 Company-environment readiness assessment

Status: In progress
Owner: implementer
Phase: P6
Product relation: OPS-BOUNDARY-001, DATA-RISK-001, DEPLOY-READINESS-001

## 目的

完成した localhost 版 ProxyConsole を会社環境候補として評価するため、現状の trust boundary、保存データ、listen port、証明書、Docker socket、依存関係、容量、backup / restore、監査可能性を実証ベースで整理し、「そのまま利用可能」「設定で対応可能」「コード変更が必要」「会社判断が必要」を区別する。会社環境へ自動展開せず、公開化や認証方式を独断で決めない。

## スコープ

含む:

- container / network / host port / localhost management boundary の inventory
- HTTP capture、headers、body、replay draft、rule、route、notification、certificate key の data inventory
- Docker socket mount と実際に使用する Docker API operation の inventory
- certificate generation / storage / replacement / expiry の現状確認
- dependency / image / license / version pinning の inventory
- capture retention、notification growth、disk exhaustion behavior の確認
- configuration / SQLite / captures / blobs / certificates の backup / restore 検証
- log / incident / capture による運用監査可能性の確認
- WSL / Docker Desktop での再現可能な readiness check command
- company policy へ確認すべき decision list と、機能を壊さない hardening 順序

含まない:

- 会社環境への deployment
- 公開インターネットへの管理画面公開
- 認証方式、SSO、RBAC の独断実装
- raw capture を不可逆に削除・マスクする仕様変更
- certificate authority、secret manager、external backup service の選定
- 実在する会社データ・認証情報・秘密鍵の収集

## 機能ルール

1. assessment は実コード、Compose、runtime command、generated artifact に基づき、推測を confirmed fact として記載しない。
2. secret の有無を確認しても値を出力・commit しない。synthetic test data のみ使用する。
3. localhost-only 前提と、外部公開時に追加で必要な制御を分離する。
4. capture fidelity と secret masking / irreversible deletion を混同しない。候補は保存時除外、表示時 masking、選択削除を分けて評価する。
5. Docker socket は現在必要な read operation と write / lifecycle operation を区別する。
6. backup / restore は archive 作成だけで完了とせず、隔離した synthetic dataset を復元して route / capture / draft / rule / notification を読み戻す。
7. 既存 P1〜P5 機能を変更する必要がある場合、assessment では具体的な後続 task と acceptance を提案し、無断実装しない。
8. company policy が不明な項目は blocking decision として明示するが、プロジェクト全体を失敗扱いにしない。

## 受入条件

1. DEV-001〜DEV-042 の全 test が引き続き成功する。
2. host に公開される port、bind address、container network、Docker socket、volume mount を機械的に一覧化できる。
3. management API / console が既定で localhost boundary に留まることを runtime で確認し、外部 bind 時の影響を明記する。
4. 保存データ種別ごとに location、format、retention、機密性、backup 対象、削除方法を表にする。
5. certificate / private key の生成場所、権限、Git除外、交換手順、期限確認方法を記録する。
6. Docker socket に対して現在使用する API endpoint / operation と必要権限をコードから列挙する。
7. direct / transitive dependency、base image、ライセンス、version pinning の現状を再現可能な command で出力する。取得不能項目は理由を記録する。
8. disk usage と retention hard limit、notification / SQLite growth、disk-full 時の影響と回復手順を確認する。
9. synthetic data を使った backup / restore test で route、capture、draft、rule、notification の読み戻しを証明する。
10. ローカル運用 runbook に startup、health、config test、backup、restore、cleanup、certificate replacement、incident確認を含める。
11. readiness matrix で各項目を `ready` / `config_required` / `code_change_required` / `company_decision_required` に分類し、証拠と推奨後続 task を紐付ける。
12. assessment command と生成文書が secret、private key、runtime capture body を Git に追加しない。

## 失敗時の扱い

- 実在会社データ、会社ポリシー、CA、SSO、secret manager が必要な項目は `company_decision_required` とし、利用者判断を待つ。
- backup restore で synthetic data を読み戻せない場合は blocking finding とし、G6 を通過させない。
- localhost boundary が既定で成立しない場合は blocking finding とし、後続修正 task を作る。
- security finding を理由に既存ローカル版を削除・停止しない。
