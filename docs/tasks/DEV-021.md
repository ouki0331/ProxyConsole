# DEV-021 Docker discovery と route target 選択

Status: Ready for review  
Owner: orchestrator  
Phase: P3  
Product relation: ROUTE-DOCKER-001, ROUTE-DOCKER-002, ROUTE-HOST-002

## 目的

現在の Docker container と port を取得し、route upstream 候補として選択できる control plane core を実装する。Docker が利用できない場合や対象がない場合も、既存の手動 host/port 指定を維持する。

- `/AGENTS.md`
- `/.agents/README.md`
- `/docs/development/WORKFLOW.md`
- `/docs/reviews/DEV-020-review-001.md`
- この文書

## スコープ

含む:

- Docker container/service discovery
- container ID/name、稼働状態、network、内部/exposed/published port の取得
- ProxyConsole 自身を既定で候補から除外し、明示指定で表示できる filter
- container と port から route の upstream scheme/host/port を構築する target selection
- 同一 container/port を複数 route で再利用
- stopped/restarted 状態を refresh または polling で反映
- Docker discovery が利用不能でも手動 host/port route を作成可能
- local HTTP API と CLI
- 自動 integration test

含まない:

- Web 管理 UI（DEV-022）
- capture viewer/replay editor
- security hardening、Docker socket 最小権限化、認証、権限分離
- Docker container の作成、削除、start/stop 操作

## 機能ルール

1. discovery は route を暗黙に作成または変更しない。
2. running/stopped を区別し、状態を API/CLI から確認できる。
3. container の複数 port は独立した upstream 候補として扱う。
4. network 内で到達可能な container name/alias と internal port を優先し、published host port の情報も保持する。
5. ProxyConsole 自身は既定一覧から除外するが、`include_self` 相当の明示指定で取得できる。
6. 同一 target を複数 route で利用できる。
7. discovery failure は既存 route と手動 route 管理を停止させない。
8. stopped/restarted 後の再取得で古い状態を成功状態として残さない。

## 受入条件

1. DEV-001〜DEV-020 の全 test が引き続き成功する。
2. API/CLI で container ID/name、状態、network、内部/exposed/published port を一覧できる。
3. running container の port が route target 候補として列挙される。
4. stopped container が stopped として反映され、既定で live target と誤認されない。
5. ProxyConsole 自身の既定除外と明示 include の両方を検証できる。
6. 発見した target から route を作成し、実際の request が選択 container/port に到達する。
7. 同一 discovered target を参照する複数 route が正しく応答する。
8. discovery が利用不能または候補がない場合も manual target route が作成・反映できる。
9. container restart/recreate 後の refresh で最新状態が返る。
10. discovery 操作が既存 route、capture、index、retention を停止させない。
11. 一つの自動 test command で全ルールを再現できる。

## 実装上の既定

- 現在の単一 compose stack で再現可能な integration test を優先する。
- Docker access は control plane service に集約し、Web UI が socket を直接扱わない境界を維持する。
- route model は DEV-020 を再利用し、Docker 固有情報を必須 field にしない。
- container name/ID の一時性を考慮し、選択時に route へ解決済み upstream を保存する。必要なら discovery metadata を任意 field として保持する。
- hardening は P6 で評価し、現在は機能結果を優先する。

## 失敗時の扱い

- Docker 接続自体が機能せず、自動 test で候補を一件も取得できない場合は `Ready for review` にしない。
- discovery failure が既存 route を停止させる場合は `Blocked` とする。
- security hardening を理由に task を停止しない。

### 発見事項

- Docker Desktop / Colima 環境では同一ホスト上に別プロジェクトのコンテナが多数存在し得るため、`DockerDiscoveryService` の既定スコープ（`scope="project"`）では同一 Compose プロジェクト（`com.docker.compose.project == "proxyconsole-dev001"`）、ProxyConsole ネットワーク接続コンテナ、または `proxyconsole.discoverable=true` ラベルを持つコンテナに絞り込み、`scope="all"` 指定でホスト全体も参照できる設計とした。
- Docker Engine Socket（`/var/run/docker.sock`）へのアクセスは `control-api` コンテナのみに限定し、`scripts/capture-ctl.sh` も稼働中の `control-api` を優先して CLI を実行することで、他のコンテナに Docker ソケット権限を広げずに CLI / API の一貫性を維持できた。
