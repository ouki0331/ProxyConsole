# DEV-030 Request draft / replay / export core

Status: In progress
Owner: implementer
Phase: P4
Product relation: CAPTURE-DETAIL-001, REPLAY-EDIT-001, REPLAY-SEND-001, REPLAY-EXPORT-001

## 目的

保存済みの replayable request から編集可能な draft を作成し、query、headers、cookies、JSON、URL-encoded form を人間可読の形で変更して安全に再送し、同じ内容を cURL / fetch として出力できる local API / CLI core を実装する。後続の Web editor が raw capture を再解釈せず、この core をそのまま利用できる契約を固定する。

## スコープ

含む:

- replayable capture から request draft を生成
- method、scheme、authority/host、path の表示と編集
- 重複・順序を保持する query/header editor model
- Cookie header の解析 view と再構築
- JSON body の構造化表示・編集・再 encode
- `application/x-www-form-urlencoded` の重複 key を保持する表示・編集・再 encode
- raw/text body fallback と content type/body metadata 表示
- URL percent-decoding した人間可読 view と送信時の正しい再 encode
- replay 前の request normalization
- hop-by-hop header 除外と `Content-Length` 再計算
- replayable/non-replayable 判定と明示 error
- cURL と browser fetch JavaScript export
- POST/PUT/PATCH/DELETE の副作用 warning metadata
- local HTTP API と CLI
- draft/replay/export の自動 integration test

含まない:

- Web request editor UI（DEV-031）
- multipart file の任意編集（初期 core では metadata/raw fallback とし、既存 exact replay を壊さない）
- WebSocket frame replay/edit
- gRPC message replay/edit
- live interception / request pause
- 自動 request modification rule（P5）
- security hardening、認証、機密値 filter（P6）

## 機能ルール

1. draft は元 capture を変更せず、新しい一時/永続 draft ID を持つ。
2. query と headers は list-of-pairs として重複・順序を保持する。
3. percent-decoded view と wire representation を区別し、decode/encode の往復で意味を変えない。
4. JSON と URL-encoded form は構造化 edit を提供し、解析不能時は raw fallback と明示 error を返す。
5. replay 時は `Connection` 等の hop-by-hop header を送らず、body 変更後の `Content-Length` を再計算する。
6. `complete` かつ必要 body blob が存在する record だけを replayable とし、truncated/metadata-only/capture-failed/missing blob は理由付きで拒否する。
7. GET/HEAD 以外、特に POST/PUT/PATCH/DELETE は副作用 warning を返すが、local user の明示 replay 操作自体は阻止しない。
8. export は現在の draft 内容を反映し、元 capture の古い値を混在させない。
9. cURL export は shell quoting、fetch export は JavaScript string/body encoding を再現可能にする。
10. replay request 自体も通常の inspector/capture/index/retention chain を通過し、新しい capture として識別できる。

## 受入条件

1. DEV-001〜DEV-022 の全 test が引き続き成功する。
2. replayable capture から draft を作成し、元 capture が不変である。
3. duplicate query/header の順序を保持したまま一項目を追加・変更・削除できる。
4. percent-encoded Unicode、space、reserved character を人間可読に編集し、送信時に意味を保って再 encode できる。
5. JSON の nested field と URL-encoded form の重複 key を編集して target が期待値を受信する。
6. cookie view の追加・変更・削除が送信 Cookie header に反映される。
7. body 変更後に hop-by-hop header が除外され、Content-Length が正しく再構築される。
8. GET/POST/PUT/PATCH/DELETE の replay が指定 route/target へ到達し、非安全 method に warning metadata がある。
9. truncated、metadata-only、capture-failed、missing blob の replay が理由付きで拒否され、target に到達しない。
10. draft から生成した cURL と fetch が syntactically valid で、少なくとも代表的な JSON/form request について同じ target-observable semantics を再現する。
11. replay 後に新 capture が検索可能となり、元 capture ID/draft ID/replay relation を追跡できる。
12. service/container restart 後の draft persistence 方針が実装と文書で一致する。永続化する場合は read-back、しない場合は明示 expiry/not-found を検証する。
13. 一つの自動 test command で draft、editing、replay、export、failure cases を再現できる。

## 実装上の既定

- capture raw bytes と derived view の境界を維持し、draft edit で保存済み capture/blob を上書きしない。
- DEV-002 の semantic replay と DEV-010 detail/index API を再利用し、別の replay engine を重複実装しない。
- editor model は後続 Web UI から扱いやすい JSON contract としつつ、wire fidelity を優先する。
- draft persistence は SQLite を既定とし、明示 delete/expiry を設ける。別方式を選ぶ場合は restart behavior と理由を task 文書に記録する。
- export string を実行する機能は不要で、生成結果と独立した test execution で再現性を検証する。
- security hardening を理由に task を停止しない。

## 失敗時の扱い

- draft edit が元 capture/blob を変更する場合は `Blocked` とする。
- duplicate query/header または body encoding の意味を保持できない場合は `Ready for review` にしない。
- non-replayable record が target へ送信される場合は即時停止し、既存 capture data を保持して修正する。
- security hardening を理由に task を停止しない。
