# DEV-010 耐久インデックスとリクエスト検索

Status: Ready for review
Owner: orchestrator
Phase: P2

## 目的

DEV-002 の原始 capture/blob を正として保持したまま、再起動後も利用できる検索 index と list/detail interface を追加する。後続の管理 UI が直接利用できる安定した検索境界を作る。

## スコープ

含む:

- 永続 metadata index
- 既存 `captures/*.json` からの初回 import と再構築
- 新規 capture の index 反映
- request list interface
- request detail interface
- pagination と安定した並び順
- time、host/authority、method、path、capture status、response status の filter
- 原始 metadata、body metadata、derived view への detail access
- index の再起動永続性と idempotent rebuild
- 自動 integration test

含まない:

- 24時間/20 GB/hard limit cleanup（DEV-011）
- Web 管理 UI
- route 管理
- Docker discovery
- replay editor
- security hardening、認証、権限分離、機密情報 filter

## データ境界

- `captures/*.json` と `blobs/*.bin` が原始記録である。
- index は削除して再構築できる派生状態とする。
- index failure が proxy routing または原始 capture 保存を停止させてはならない。
- body bytes を index DB に重複保存しない。
- schema version と migration/rebuild 方針を明記する。

## 受入条件

1. DEV-001/DEV-002 の全 test が引き続き成功する。
2. 既存 capture を index に import できる。
3. 同じ capture を再 import しても重複 row が作成されない。
4. 新しい request が検索結果へ反映される。
5. list は新しい順を既定とし、同一 timestamp でも順序が安定する。
6. pagination で欠落または重複が発生しない。
7. time range、authority/host、method、path、capture status、response status を個別および組み合わせて filter できる。
8. detail から ordered headers/query、body size/SHA-256/status/blob reference、derived views を取得できる。
9. process/container restart 後も index と検索が利用できる。
10. index を削除して原始 capture から rebuild すると同じ件数と主要 metadata が復元される。
11. 破損した一件の capture が存在しても、他の record の import/query と proxy routing は継続し、失敗 record を識別できる。
12. 一つの自動 test command で上記を再現できる。

## 実装上の既定

- ローカル単一ユーザー用途なので、外部 DB server を追加せず embedded storage を優先する。
- 後続 UI が利用できるよう、CLI だけに閉じず local HTTP API または同等の安定した interface を提供する。
- framework 選択より、既存 capture format 互換性と自動 test を優先する。

## 失敗時の扱い

- index 実装が原始 capture の書き込みを同期的に阻害する場合、非同期 import/rebuild へ分離する。
- 既存 DEV-002 record を破棄または不可逆変換しなければ進めない場合は `Blocked` とする。
- security hardening を理由に task を停止しない。

## 実装 Agent 記入欄

### 実装要約

- **永続メタデータインデックスと Migration (`migrations/001_capture_index.sql`, `services/recorder/index_store.py`)**:
  - `captures/*.json` と `blobs/*.bin` を唯一の原始記録（Source of Truth）として維持したまま、SQLite (`database/captures.sqlite3`, WAL モード) に検索用メタデータのみを保存する派生インデックスを実装した（raw body bytes は DB に重複保存しない）。
  - `schema_migrations` テーブルでスキーマバージョン (`1`) を管理し、`captures_index` テーブルで `capture_id` を主キーとして `ON CONFLICT(capture_id) DO UPDATE` による冪等 upsert を実装した。
  - 破損した `captures/*.json` が存在する場合は `capture_import_errors` テーブルにファイル名・エラー種別・メッセージを記録して隔離し、他の正常レコードの import・検索およびプロキシ転送を停止させない構造とした。
  - インデックス DB を削除して `captures/*.json` から完全再構築する `rebuild_index()` を実装した。
- **リアルタイム Index 反映と障害隔離 (`services/recorder/addon.py`)**:
  - `inspector` 起動時に既存 `captures/*.json` を自動 import し、各リクエスト保存時には原始 JSON/blob 保存完了後に fault-isolated な `try/except` ブロックで SQLite インデックスへ即時反映する。
- **List / Detail ローカル HTTP API と CLI (`services/recorder/api_server.py`, `services/recorder/capture_cli.py`, `scripts/capture-ctl.sh`)**:
  - 後続の管理 UI が直接利用できるローカル HTTP API (`http://127.0.0.1:${CONTROL_API_PORT:-18480}`) として `GET /api/v1/captures`（一覧・検索）、`GET /api/v1/captures/<id>`（詳細・順序付き headers/query・body metadata・派生ビュー）、`GET /api/v1/index/status`、`POST /api/v1/index/import`、`POST /api/v1/index/rebuild` を実装した。
  - CLI (`./scripts/capture-ctl.sh search|list|get|detail|import|rebuild|index-status`) でも同等の検索・詳細取得・再構築を提供した。
  - 並び順は `(captured_at_unix_us DESC, capture_id DESC)` を既定とし、同一タイムスタンプを持つ複数レコード間でも `capture_id` のタイブレークによりページネーション時の欠落・重複が発生しない厳密な全順序を保証した。

   - 不正 JSON ファイル `captures/cap-corrupt-0001.json` が存在する状態で import・検索・新規プロキシ通信を実行し、`import_errors` で破損ファイルを特定できること、他レコードの検索および新規リクエストのプロキシ転送（HTTP `200`）が停止しないことを確認 (`PASS`)。

### 未検証事項

- 24 時間 / 20 GB / hard limit に基づく古い capture/blob と index 行の自動パージ（次タスク `DEV-011` の対象）。
- Web 管理 UI からのブラウザ検索操作（P4 の対象）。

### 発見事項

- ホスト環境（Colima）で `18080` ポートが SSH フォワーダにより占有されていたため、ローカル管理 API の既定ポートは衝突を回避できる `CONTROL_API_PORT=18480` とし、環境変数または `.env` で変更可能とした。
- `mitmproxy/mitmproxy` ベースイメージでは `mitmdump` 実行時のみ `gosu mitmproxy` で権限降格されるため、`control-api` および `capture-ctl.sh` でも `gosu mitmproxy` を使用して SQLite WAL/SHM ファイルの所有者不一致（readonly database エラー）を防止した。また、仮に権限不整合が起きても `addon.py` の fault isolation により原始 capture 保存とプロキシ転送が停止しないことも実測で確認できた。
