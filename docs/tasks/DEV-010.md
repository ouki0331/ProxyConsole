# DEV-010 耐久インデックスとリクエスト検索

Status: In progress
Owner: implementer
Phase: P2  
Product relation: TRACE-CAP-001, TRACE-CAP-002, TRACE-DECODE-001

## 目的

DEV-002 の原始 capture/blob を正として保持したまま、再起動後も利用できる検索 index と list/detail interface を追加する。後続の管理 UI が直接利用できる安定した検索境界を作る。

- この文書

## スコープ

含む:

- 永続 metadata index
- 既存 `captures/*.json` からの初回 import と再構築
- 新規 capture の index 反映
- request list interface
- request detail interface
- pagination と安定した並び順
- time、host/authority、method、path、capture status、response status の filter
- 原始 metadata、body metadata、derived view への detail access
- index の再起動永続性と idempotent rebuild
- 自動 integration test

含まない:

- 24時間/20 GB/hard limit cleanup（DEV-011）
- Web 管理 UI
- route 管理
- Docker discovery
- replay editor
- security hardening、認証、権限分離、機密情報 filter

## データ境界

- `captures/*.json` と `blobs/*.bin` が原始記録である。
- index は削除して再構築できる派生状態とする。
- index failure が proxy routing または原始 capture 保存を停止させてはならない。
- body bytes を index DB に重複保存しない。
- schema version と migration/rebuild 方針を明記する。

## 受入条件

1. DEV-001/DEV-002 の全 test が引き続き成功する。
2. 既存 capture を index に import できる。
3. 同じ capture を再 import しても重複 row が作成されない。
4. 新しい request が検索結果へ反映される。
5. list は新しい順を既定とし、同一 timestamp でも順序が安定する。
6. pagination で欠落または重複が発生しない。
7. time range、authority/host、method、path、capture status、response status を個別および組み合わせて filter できる。
8. detail から ordered headers/query、body size/SHA-256/status/blob reference、derived views を取得できる。
9. process/container restart 後も index と検索が利用できる。
10. index を削除して原始 capture から rebuild すると同じ件数と主要 metadata が復元される。
11. 破損した一件の capture が存在しても、他の record の import/query と proxy routing は継続し、失敗 record を識別できる。
12. 一つの自動 test command で上記を再現できる。

## 実装上の既定

- ローカル単一ユーザー用途なので、外部 DB server を追加せず embedded storage を優先する。
- 後続 UI が利用できるよう、CLI だけに閉じず local HTTP API または同等の安定した interface を提供する。
- framework 選択より、既存 capture format 互換性と自動 test を優先する。

## 失敗時の扱い

- index 実装が原始 capture の書き込みを同期的に阻害する場合、非同期 import/rebuild へ分離する。
- 既存 DEV-002 record を破棄または不可逆変換しなければ進めない場合は `Blocked` とする。
- security hardening を理由に task を停止しない。
