# DEV-001 最小プロキシチェーンの構築

Status: Done
Owner: none
Phase: P1  
Product relation: ROUTE-HOST-001, TRACE-CAP-001

## 目的

一つの外部 HTTPS 入口から、記録層を経由し、Host に応じて二つの target へ正しく転送できる最小構成を作る。後続の capture/replay 検証に使用できる再現可能な土台を残す。

## 必須コンテキスト

作業前に次だけを読むこと。

- `/AGENTS.md`
- `/docs/development/WORKFLOW.md`
- `/docs/architecture/REPOSITORY_LAYOUT.md`
- `/docs/architecture/CAPTURE_CONTRACT.md`
- この文書

過去の会話は不要である。

## スコープ

含む:

- Docker Compose によるローカル構成
- Nginx edge: TLS 終端
- traffic inspector: 第一候補 mitmproxy
- Nginx internal router: Host routing
- 二つの識別可能な Echo target
- 開発用証明書の生成手順。秘密鍵は commit しない
- 起動、停止、検証を再現する script または Make target
- GET と小さな POST の black-box test
- 検証結果の文書化

含まない:

- 長期保存 schema
- DB
- 管理 UI
- Docker discovery
- リプレイ UI/実装
- 自動 request modification
- 通知
- 80/443 の強制使用。開発時は衝突回避可能な port を既定値にし、設定で 443 に変更可能とする

## 必須トポロジー

```text
client
  -> nginx edge (HTTPS)
  -> inspector
  -> nginx internal router (Docker network only)
  -> echo-a or echo-b
```

inspector が Host を保持し、internal router が Host によって target を選択すること。internal router を host へ publish しない。

## 受入条件

1. 一つのコマンド列で fresh clone から起動できる。
2. `app-a` 用 Host の GET が echo-a の識別子を返す。
3. `app-b` 用 Host の GET が echo-b の識別子を返す。
4. JSON POST の method、path、query、body が target で確認できる。
5. 誤った Host は target に転送されず、明示的な 404 または拒否になる。
6. internal router port は host に公開されない。
7. inspector を停止した場合、edge は無関係の target へ誤配送しない。観測された status を記録する。
8. `docker compose config` と Nginx config test が成功する。
9. 自動 black-box test が成功し、その実行コマンドと結果要約がこの文書に追記される。
10. secret、生成秘密鍵、runtime capture が Git status に出ない。

## 失敗時の扱い

- mitmproxy の固定 reverse target と Host 保持が成立しない場合、無理に独自 proxy を実装せず `Blocked` として証拠を push する。
- TLS 開発証明書の OS trust は必須条件ではない。test client の明示的な開発用設定で検証してよい。
- Docker または image pull が環境制約で動かない場合、構成ファイル検証まで行い、実行未検証を明記して `Blocked` とする。

## 実装 Agent 記入欄

### 実装要約

- **Docker Compose トポロジー (`deploy/compose/docker-compose.yml`)**:
  - `edge` (Nginx 1.27-alpine): 外部 HTTPS 終端を担当。ホスト公開ポートは `${EDGE_HTTPS_PORT:-8443}:443` のみとし、既定値 `8443` から環境変数または `.env` で `443` へ変更可能とした。
  - `inspector` (mitmproxy `mitmdump`): `--mode reverse:http://router:8080 --set keep_host_header=true` で起動し、クライアントからの `Host` ヘッダーを変更せず内部ルーターへ転送する。
  - `router` (Nginx 1.27-alpine): Docker 内部ネットワーク専用とし、ホストへポートを公開しない (`expose: ["8080"]` のみ)。`app-a.local.test` を `echo-a:8080`、`app-b.local.test` を `echo-b:8080` へ振り分け、未知の `Host` は `default_server` で明示的に `404` JSON (`{"error":"unknown_host",...}`) を返す。
  - `echo-a` / `echo-b` (`tests/helpers/echo_server.py`, Python 3.12-alpine): 各自の `TARGET_ID` (`echo-a` / `echo-b`)、HTTP メソッド、raw path、raw query、順序付きクエリ配列、順序付きヘッダー配列、リクエストボディ文字列・JSON・サイズを返す。
  - ネットワーク分離: `edge_inspector_net`、`inspector_router_net` (`internal: true`)、`router_targets_net` (`internal: true`) の3ネットワークに分離し、`edge` が `inspector` をバイパスして `router` や `echo-*` へ直接通信できない構造にした。
- **証明書生成手順 (`deploy/certificates/openssl.cnf`, `deploy/certificates/README.md`, `scripts/generate-certs.sh`)**:
  - 自己署名証明書・秘密鍵を Git 管理外の `var/certificates/edge.crt` および `var/certificates/edge.key` に生成するスクリプトと手順書を作成した。
- **再現スクリプト・テスト (`scripts/up.sh`, `scripts/down.sh`, `scripts/verify-config.sh`, `tests/integration/test_proxy_chain.sh`, `Makefile`)**:
  - `make up` / `make down` / `make config-test` / `make test` / `make clean` で fresh clone から証明書生成・ビルド・起動・検証・停止を一貫実行できるようにした。

### 実行した検証

以下のコマンドでクリーン状態からの起動、構成テスト、black-box 統合テスト、停止を一貫実行し、全項目が成功することを確認した。

```bash
make clean && make test && make down
```

（内部で `./scripts/verify-config.sh`、`./scripts/up.sh`、`./tests/integration/test_proxy_chain.sh`、`./scripts/down.sh` を順次実行）

検証結果の要約:

1. **構成検証 (`./scripts/verify-config.sh`)**:
   - `docker compose -f deploy/compose/docker-compose.yml config -q`（既定ポート `8443` および `EDGE_HTTPS_PORT=443`）: 成功 (`PASS`)
   - `edge` コンテナの `nginx -t`: `syntax is ok` / `test is successful` (`PASS`)
   - `router` コンテナの `nginx -t`: `syntax is ok` / `test is successful` (`PASS`)
2. **内部ポート非公開検証**:
   - `docker compose ps --format json` により `inspector`、`router`、`echo-a`、`echo-b` の `PublishedPort` が存在しないことを確認 (`PASS`)。
3. **Host ルーティング検証 (GET)**:
   - `https://app-a.local.test:8443/hello-a?mode=get` -> HTTP `200`, `target="echo-a"`, `host="app-a.local.test:8443"` (`PASS`)
   - `https://app-b.local.test:8443/hello-b?mode=get` -> HTTP `200`, `target="echo-b"`, `host="app-b.local.test:8443"` (`PASS`)
4. **JSON POST 検証**:
   - `app-a.local.test` / `app-b.local.test` に対する `POST /v1/items/create?env=dev&tag=first&tag=second` (JSON body) で、`method="POST"`, `path="/v1/items/create"`, `raw_query="env=dev&tag=first&tag=second"`, `query_params=[["env","dev"],["tag","first"],["tag","second"]]`, `body_json` の完全一致を確認 (`PASS`)。
5. **不明 Host 拒否検証**:
   - `https://unknown.local.test:8443/should-not-route` -> HTTP `404` (`{"error":"unknown_host","message":"No route configured for Host","host":"unknown.local.test:8443"}`) が返り、`echo-a` / `echo-b` のいずれにも転送されないことを確認 (`PASS`)。
6. **inspector 停止時の挙動検証**:
   - `docker compose stop inspector` 実行後、`app-a.local.test` / `app-b.local.test` へのリクエストは他の target へ誤配送されず、DNS TTL (1s) 失効後は HTTP `502 Bad Gateway`（DNS キャッシュ残存中の接続試行時は `proxy_connect_timeout 3s` により HTTP `504 Gateway Time-out`）となることを観測・確認した (`PASS`)。
   - `docker compose start inspector` 実行後、再び HTTP `200` で正常ルーティングに復帰することを確認 (`PASS`)。
7. **Git status クリーン検証**:
   - `git status --porcelain` に秘密鍵 (`.key`)、証明書 (`.crt`, `.pem`)、runtime データ (`var/`, `.mitm`, `.flow`) が一切現れないことを確認 (`PASS`)。

### 未検証事項

- ホスト OS 側で特権ポート `443` を実際に bind しての通信テスト（`EDGE_HTTPS_PORT=443` での `docker compose config` 検証は実施済み。実通信テストは非特権の既定ポート `8443` で実施）。
- OS 証明書ストアへの開発用証明書登録（タスク方針に従い、`curl --cacert var/certificates/edge.crt` で明示指定して検証）。

### 発見事項

- ローカル Colima 環境のようにホスト側ワークスペースパスが Docker VM へ virtiofs マウントされていない環境では、Compose のホストファイル bind mount (`volumes:`) が VM 側で空ディレクトリとして扱われる事象を確認した。そのため、`edge`・`router`・`echo` は軽量 `Dockerfile` による `COPY` ビルド方式（Docker ソケット経由でコンテキスト転送）を採用し、ホスト bind mount 設定に依存せずどの Docker 環境でも同一手順で再現可能にした。
