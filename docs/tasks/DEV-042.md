# DEV-042 Aggregated local notifications and live event feed

Status: Ready for review
Owner: orchestrator
Phase: P5
Product relation: NOTIFY-EVENT-001, NOTIFY-AGGREGATE-001, NOTIFY-LIVE-001

## 目的

ProxyConsole が観測した HTTP 5xx、Nginx warn/error、upstream timeout、target/container unavailable を共通 event として記録・集約し、同一障害を連続通知せず、開いている localhost Web console へ WebSocket で配信し、利用者が許可した場合だけ browser system notification を表示する。

## スコープ

含む:

- HTTP 5xx、Nginx warn/error、upstream timeout、target/container unavailable の正規化 event model
- route ID と安定した fingerprint による集約
- configurable aggregation window（初期値 5 分）
- 初回発生、集約 count 更新、recovery event
- durable event / incident state と restart recovery
- event list / detail / filter / acknowledge API または CLI
- WebSocket live event feed と reconnect / resync
- Web console の Notifications workspace、状態/count/最終発生時刻/原因/route 表示
- permission request を利用者操作で行う browser notification
- WebSocket 非対応・切断時の画面上 status と手動再接続
- automated integration test と browser-level E2E

含まない:

- email、Slack、Teams、外部 webhook、push service
- HTTP 4xx の既定通知
- request/response body の通知本文への展開
- response modification、live interception、WebSocket frame inspection
- authentication、permission separation、secret filtering、public deployment hardening（P6）

## 機能ルール

1. 既定通知対象は HTTP 5xx、Nginx warn/error、502/503/504、upstream timeout、container unavailable とし、HTTP 4xx は既定で除外する。
2. fingerprint は少なくとも event type、route ID、正規化原因を含み、request ID、timestamp、動的 count を含めない。
3. 同一 route + fingerprint は既定 5 分 window 内で一つの incident に集約し、初回と意味のある count 更新だけを通知する。
4. recovery は同一 incident に関連付け、未解決から回復済みへの遷移を一度だけ通知する。
5. event ingestion、aggregation、persistence は browser 接続や notification permission に依存しない。
6. WebSocket reconnect 後は cursor / sequence を使い、欠落 event を REST resync できる。重複受信しても画面上の count を二重加算しない。
7. browser notification permission は自動要求せず、明示的な利用者操作からのみ要求する。拒否・未対応でも Web console は動作する。
8. notification payload は event type、route、count、時刻、短い理由を表示し、capture body や header 値を含めない。
9. Notifications subsystem の失敗で proxy routing、capture、rule engine、既存 Web workspace を停止しない。
10. localhost local-first とし、login UI は追加しない。

## 受入条件

1. DEV-001〜DEV-041 の全 test が引き続き成功する。
2. HTTP 500、502/503/504、upstream timeout、Nginx warn/error、停止 target/container を区別した正規化 event を生成できる。
3. HTTP 4xx は既定では event / browser notification を生成しない。
4. 同一 route + fingerprint の連続障害が 5 分 window 内で一 incident に集約され、count、first_seen、last_seen が正しく更新される。
5. 異なる route または fingerprint は別 incident となり、window 終了後の再発は新しい notification cycle として扱われる。
6. recovery を一度だけ記録し、同一 incident の resolved state、resolved_at、recovery reason を確認できる。
7. control-api / inspector restart 後も incident history と未解決 state を読み戻せる。
8. list/detail/filter/acknowledge interface で open/resolved、event type、route、time range、fingerprint を検索できる。
9. WebSocket feed が monotonically increasing sequence/cursor を持ち、open console へ initial/count-update/recovery を配信する。
10. WebSocket 切断・再接続時に欠落 event を resync し、重複 delivery で count や表示を二重反映しない。
11. Web console の Notifications workspace で incident status、severity/type、route、count、first/last/resolved time、reason、acknowledged state を一覧・詳細表示できる。
12. browser notification は利用者が Enable を押して permission が granted の場合だけ表示し、denied/default/unsupported でも画面内 feed と他 workspace が動作する。
13. Notifications API/WebSocket/persistence failure を注入しても proxy routing、capture、Rules、Routes、Docker、Requests、Replay workspace が継続利用できる。
14. keyboard、focus、label、live region、狭い画面、reconnect state を browser-level test で確認できる。
15. 一つの integration command で event classification、4xx exclusion、aggregation、recovery、restart persistence、WebSocket reconnect/resync、browser permission states、failure isolation を再現できる。

## 失敗時の扱い

- event classification や fingerprint の誤りで異なる障害を混同する場合は blocking とする。
- notification storm、count 二重加算、recovery 重複、restart 後の未解決 incident 消失は blocking とする。
- Notifications 障害が proxy routing または既存 workspace を停止する場合は blocking とする。
- OS ごとの browser notification 外観差は permission state と API 呼出を自動検証できれば non-blocking とする。
- security hardening、認証、機密情報 filter を理由に task を停止しない。

## 実装 Agent 記入欄

### 実装要約

1. **永続化スキーマとマイグレーション (`migrations/007_notifications.sql`, `services/recorder/index_store.py`)**:
   - SQLite スキーマバージョンを `7` に更新し、設定テーブル `notification_config`（`aggregation_window_seconds` 既定 `300` 秒、`notify_http_4xx` 既定 `0`）、集約インシデントテーブル `notification_incidents`、および単調増加カーソル `seq`（`INTEGER PRIMARY KEY AUTOINCREMENT`）を持つイベント履歴テーブル `notification_events` を追加。
   - `control-api` および `inspector` の再起動後も open / resolved インシデント状態、発生回数、タイムスタンプ、およびイベントシーケンス履歴が完全に復元される設計とした。

2. **正規化イベント分類・5分ウィンドウ集約・Recovery エンジン (`services/recorder/notification_engine.py`, `services/recorder/addon.py`)**:
   - `NotificationEngineManager` を実装し、`http_500`、`http_502_503_504`、`upstream_timeout`、`nginx_warn`、`nginx_error`、`container_unavailable` の6種別を正規化イベントとして分類・記録。HTTP 4xx は既定で除外（Rule 1, AC-2, AC-3）。
   - `compute_fingerprint(event_type, route_id, normalized_reason)` により、`request_id`/`capture_id` やタイムスタンプ、動的 `count`、動的 IP/PID/ポート番号を除外した安定的な `fp:<sha256_prefix>` を生成（Rule 2）。
   - 同一 `route_id + fingerprint` の未解決インシデントが設定ウィンドウ（既定5分）内に存在する場合は単一インシデントへ集約し、`count`・`suppressed_count`・`last_seen` を更新。ブラウザ通知フラグ（`browser_notify`）は初回（`count == 1`）とマイルストーン回数（`5, 10, 25, 50, 100...`）のみ `True` とし、中間の連続発生通知を抑制（Rule 3, AC-4）。
   - 異なる `route_id` または `fingerprint` は別インシデントとして記録し、集約ウィンドウ満了後の同一障害再発は `cycle_number` をインクリメントした新しい通知サイクルとして記録（AC-5）。
   - 対象ルートで正常応答（HTTP 2xx/3xx）または停止コンテナの稼働再開を検知した際、同一インシデントを `open -> resolved` へ遷移させ、`resolved_at` と `recovery_reason` を記録して `recovery` イベントを一度だけ発行（Rule 4, AC-6）。
   - 通知ペイロードには `event_type`、`route_id`、`count`、`first_seen`/`last_seen`/`resolved_at`、短い `normalized_reason` のみを格納し、リクエスト/レスポンスの body や header 値は一切含めない（Rule 8）。

3. **Nginx ログ収集・タイムアウト検証経路・REST / WebSocket / CLI インターフェース (`deploy/nginx/router/*`, `services/recorder/route_manager.py`, `services/recorder/api_server.py`, `services/recorder/capture_cli.py`)**:
   - 内部 Nginx ルーターのエラーログを共有ボリューム `/var/lib/proxyconsole/router/nginx-error.log` へ出力しつつ標準エラーへも転送する構成を追加し、`/__pc_fast_timeout`（`proxy_read_timeout 1s`）ロケーションを各ルートに生成。
   - `api_server.py` にバックグラウンド監視スレッド `_notification_monitor_worker`（Nginx warn/error ログの増分 tail と Docker ターゲットコンテナ停止/復旧監視）、RFC 6455 準拠の WebSocket エンドポイント `/api/v1/notifications/ws`（`since_seq` カーソル同期およびリアルタイム配信）、および REST API（`/api/v1/notifications/status`, `/config`, `/incidents`, `/incidents/<id>`, `/incidents/<id>/acknowledge`, `/incidents/<id>/resolve`, `/acknowledge-all`, `/recover`, `/events`, `/ingest`）を実装（Rule 5, Rule 6, AC-8, AC-9）。
   - `capture_cli.py`（`./scripts/capture-ctl.sh`）に `notification-status`、`notification-list`、`notification-get`、`notification-ack`、`notification-resolve`、`notification-events` サブコマンドを追加。

4. **Web コンソール Notifications ワークスペース・WebSocket 再接続同期・Browser Notification 権限管理 (`web/console/index.html`, `web/console/styles.css`, `web/console/app.js`)**:
   - ナビゲーションバーに `Notifications` ワークスペース切替ボタンと Live Feed 状態バッジを追加。
   - インシデント一覧テーブル（Status & Ack, Severity/Event Type, Route, Count, First/Last/Resolved Time, Reason & Fingerprint, Actions）、フィルタ検索フォーム（`status`, `event_type`, `route_id`, `fingerprint`, `acknowledged`, `since`, `until`, `q`）、インシデント詳細＆イベントシーケンスタイムライン、および Live WebSocket Event Stream パネルを実装（AC-8, AC-11）。
   - WebSocket 切断・再接続時に保持カーソル `notifLatestSeq`（`since_seq`）を用いて欠落イベントを自動・手動再同期し、処理済み `seq` セット（`notifProcessedSeqs`）により重複配信時も画面上の `count` や通知回数が二重加算されないよう保証（Rule 6, AC-10）。
   - ブラウザ通知権限（`Notification.requestPermission()`）は初期ロード時に一切要求せず、利用者が `#enable-browser-notif-btn` を明示的にクリックした時のみ要求。`granted` かつ有効化時のみシステム通知を発火し、`default`/`denied`/`unsupported` 状態でも画面内ライブフィードと全ワークスペースが正常動作することを確認（Rule 7, AC-12）。
   - Notifications API / WebSocket / 永続化障害注入時もフォールトアイソレーションによりプロキシルーティング、キャプチャ記録、Modification Rules、Routes、Docker、Requests、Replay の各ワークスペースが停止しないことを保証（Rule 9, AC-13）。

### 未検証事項

- OS ネイティブ通知センター上の視覚的なトースト外観（macOS / Windows / Linux デスクトップ通知バナーの OS 描画差）はヘッドレス環境のため、`window.Notification` API の権限状態遷移（`default` / `granted` / `denied` / `unsupported`）およびコンストラクタ呼び出し引数・ペイロード検証によって自動確認している（タスク仕様「失敗時の扱い」に基づき non-blocking）。

### 発見事項

- Nginx エラーログの増分 tail と mitmproxy フロー観測の双方で upstream timeout が検知される場合、同一タイムアウトが `upstream_timeout` と `nginx_error` に二重計上されないよう、ライブ tail 時は `upstream timed out` 行を `observe_http_flow` 側の `upstream_timeout` 分類へ一元化し、それ以外の Nginx `[warn]` / `[error]` 行を `nginx_warn` / `nginx_error` として取り込むことで、正確なイベント分類を実現した。
