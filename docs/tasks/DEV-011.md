# DEV-011 保持期間と容量上限による自動クリーンアップ

Status: In progress
Owner: implementer
Phase: P2  
Product relation: TRACE-CAP-001, TRACE-CAP-002

## 目的

capture、blob、index の整合性を維持しながら、24時間の最短保持、soft 20 GB、設定可能な hard limit に基づいて古い記録を自動削除できるようにする。ローカルディスクが無制限に増加しない、観測可能で再現可能な retention 機能を提供する。

## スコープ

含む:

- 最短保持期間（既定24時間）
- soft 容量目標（既定20 GB）
- 設定可能な hard 容量上限
- hard limit 到達時の保持期間を超えた強制削除
- 最古 record からの決定的な削除順
- capture JSON、body blob、index row の一貫した削除
- 欠損 blob、孤立 blob、破損 capture の cleanup/reconciliation
- retention status、dry-run、手動実行 interface
- 定期自動実行
- 削除件数、解放 bytes、残容量、実行理由の履歴
- 小さい test threshold を使用した自動 integration test

含まない:

- 実際に20 GBの test data を生成すること
- Web 管理 UI
- route 管理、Docker discovery
- replay editor
- security hardening、認証、権限分離、機密情報 filter

## ルールと優先順位

1. 通常時は24時間以内の record を保持する。
2. 使用量が soft target を超えた場合、24時間を超えた最古 record から削除して soft target 以下を目指す。
3. 使用量が hard limit を超えた場合、年齢に関係なく最古 record から削除して hard limit 以下にする。
4. hard limit は最短保持期間より優先する。
5. 同一 timestamp の削除順は capture ID で安定させる。
6. 削除途中の失敗で index が存在するのに原始 record の状態が不明になる場合、次回 reconciliation で復旧可能にする。

## 受入条件

1. DEV-001、DEV-002、DEV-010 の全 test が引き続き成功する。
2. soft target 以下では record を削除しない。
3. soft target 超過時、24時間以内の record を残し、期限超過の最古 record から削除する。
4. 1日分が soft target を超える場合でも、hard limit 未満なら24時間以内の record を保持する。
5. hard limit 超過時、24時間以内を含め最古 record から削除し、hard limit 以下に戻す。
6. capture JSON、対応 blob、index row が同じ cleanup 結果になる。
7. `truncated`、`metadata-only`、bodyなし record も正しい byte size と削除動作を持つ。
8. 欠損 blob、孤立 blob、破損 capture が cleanup 全体を停止させず、結果で識別できる。
9. dry-run は削除対象と予定解放量を返し、filesystem/index を変更しない。
10. 手動 cleanup と定期 cleanup が同じ engine と policy を使用する。
11. restart 後も policy 設定と直近実行履歴を確認できる。
12. 小さい容量値と合成 timestamp を使う一つの自動 test command で全ルールを再現できる。

## 実装上の既定

- byte 使用量は capture JSON、blob、index DB と retention が管理する関連ファイルを対象にする。計算範囲を文書化する。
- test では KB/MB 単位の configurable threshold を使い、20 GB data を作らない。
- cleanup は proxy request path から分離し、失敗しても routing/capture を止めない。
- API/CLI は DEV-010 の control interface を拡張してよい。

## 失敗時の扱い

- 原始 capture と index を一貫して削除できない場合は `Blocked` とし、P3 へ進まない。
- cleanup failure が proxy routing/capture を停止する場合は fault isolation を修正する。
- security hardening を理由に task を停止しない。
