# DEV-011 保持期間と容量上限による自動クリーンアップ

Status: Ready for review
Owner: orchestrator
Phase: P2  
Product relation: TRACE-CAP-001, TRACE-CAP-002

## 目的

capture、blob、index の整合性を維持しながら、24時間の最短保持、soft 20 GB、設定可能な hard limit に基づいて古い記録を自動削除できるようにする。ローカルディスクが無制限に増加しない、観測可能で再現可能な retention 機能を提供する。

## スコープ

含む:

- 最短保持期間（既定24時間）
- soft 容量目標（既定20 GB）
- 設定可能な hard 容量上限
- hard limit 到達時の保持期間を超えた強制削除
- 最古 record からの決定的な削除順
- capture JSON、body blob、index row の一貫した削除
- 欠損 blob、孤立 blob、破損 capture の cleanup/reconciliation
- retention status、dry-run、手動実行 interface
- 定期自動実行
- 削除件数、解放 bytes、残容量、実行理由の履歴
- 小さい test threshold を使用した自動 integration test

含まない:

- 実際に20 GBの test data を生成すること
- Web 管理 UI
- route 管理、Docker discovery
- replay editor
- security hardening、認証、権限分離、機密情報 filter

## ルールと優先順位

1. 通常時は24時間以内の record を保持する。
2. 使用量が soft target を超えた場合、24時間を超えた最古 record から削除して soft target 以下を目指す。
3. 使用量が hard limit を超えた場合、年齢に関係なく最古 record から削除して hard limit 以下にする。
4. hard limit は最短保持期間より優先する。
5. 同一 timestamp の削除順は capture ID で安定させる。
6. 削除途中の失敗で index が存在するのに原始 record の状態が不明になる場合、次回 reconciliation で復旧可能にする。

## 受入条件

1. DEV-001、DEV-002、DEV-010 の全 test が引き続き成功する。
2. soft target 以下では record を削除しない。
3. soft target 超過時、24時間以内の record を残し、期限超過の最古 record から削除する。
4. 1日分が soft target を超える場合でも、hard limit 未満なら24時間以内の record を保持する。
5. hard limit 超過時、24時間以内を含め最古 record から削除し、hard limit 以下に戻す。
6. capture JSON、対応 blob、index row が同じ cleanup 結果になる。
7. `truncated`、`metadata-only`、bodyなし record も正しい byte size と削除動作を持つ。
8. 欠損 blob、孤立 blob、破損 capture が cleanup 全体を停止させず、結果で識別できる。
9. dry-run は削除対象と予定解放量を返し、filesystem/index を変更しない。
10. 手動 cleanup と定期 cleanup が同じ engine と policy を使用する。
11. restart 後も policy 設定と直近実行履歴を確認できる。
12. 小さい容量値と合成 timestamp を使う一つの自動 test command で全ルールを再現できる。

## 実装上の既定

- byte 使用量は capture JSON、blob、index DB と retention が管理する関連ファイルを対象にする。計算範囲を文書化する。
- test では KB/MB 単位の configurable threshold を使い、20 GB data を作らない。
- cleanup は proxy request path から分離し、失敗しても routing/capture を止めない。
- API/CLI は DEV-010 の control interface を拡張してよい。

## 失敗時の扱い

- 原始 capture と index を一貫して削除できない場合は `Blocked` とし、P3 へ進まない。
- cleanup failure が proxy routing/capture を停止する場合は fault isolation を修正する。
- security hardening を理由に task を停止しない。

## 実装 Agent 記入欄

### 実装要約

- **スキーマと永続化 (`migrations/002_retention_policy.sql`, `services/recorder/index_store.py`)**:
  - `retention_policy` テーブル（最短保持期間 既定 `86400` 秒 / 24h、soft 容量目標 既定 `21474836480` bytes / 20 GiB、hard 容量上限 既定 `26843545600` bytes / 25 GiB、定期実行間隔 既定 `60.0` 秒、定期実行有効フラグ）と、直近実行履歴を保持する `retention_runs` テーブルを追加した。
  - インデックス再構築 (`rebuild_index`) 時も `retention_policy` と `retention_runs` を退避・復元し、設定と履歴が失われないようにした。
- **Retention & Reconciliation Engine (`services/recorder/retention.py`, `docs/architecture/CAPTURE_CONTRACT.md`)**:
  - 容量計算範囲 (`calculation_scope`) を `captures/*.json + blobs/*.bin + database/captures.sqlite3 (+ -wal, -shm)` として定義・文書化し、各 record の回収可能サイズを `record_bytes + blob_bytes`（`metadata-only` や空 body は `blob_bytes = 0`、`truncated` は部分保存 blob の実サイズ）として計算した。
  - 最古優先・同一 timestamp は `capture_id` 昇順 (`captured_at_unix_us ASC, capture_id ASC`) の決定的な順序で評価し、(1) `total_bytes <= soft_limit_bytes` では削除しない、(2) `soft_limit_bytes < total_bytes <= hard_limit_bytes` では最短保持期間（24h）を超過した record のみを最古順で削除し 24h 以内の record は保持する、(3) `total_bytes > hard_limit_bytes` では保持期間に関わらず最古順で `hard_limit_bytes` 以下になるまで削除する優先順位を実装した。
  - 孤立 blob (`orphan_blobs`)、破損 capture JSON (`corrupt_captures`)、欠損 blob (`missing_blobs`：`capture-failed` / `replayable: false` / `blob_ref: null` へ reconciliation)、および中断等による不整合 index row (`dangling_index_capture_ids`) を cleanup を停止させずに処理・識別できるようにした。
  - `dry_run=True` では削除予定 record・異常項目・予定解放 bytes・予定残容量を計算して返し、filesystem と SQLite index を一切変更しない。
- **HTTP API / CLI / 定期自動実行 (`services/recorder/api_server.py`, `services/recorder/capture_cli.py`, `tests/integration/test_retention_cleanup.sh`, `Makefile`)**:
  - Control API に `GET /api/v1/retention/status`、`GET|PUT|POST /api/v1/retention/policy`、`POST /api/v1/retention/run` (`dry_run`, `now` 対応) を追加し、`control-api` 内に同じ `RetentionEngine` と policy を用いる定期バックグラウンド実行スレッドを追加した。
  - CLI (`capture_cli.py` / `scripts/capture-ctl.sh`) に `retention-status`、`retention-policy`、`retention-run` (`--dry-run`, `--now`) を追加した。
  - 小さい容量閾値と合成 timestamp を用いて受入条件 1〜12 を網羅検証する自動統合テスト `tests/integration/test_retention_cleanup.sh` を作成し、`Makefile` の `test` ターゲットへ統合した。

### 発見事項

- SQLite WAL モードでは削除・履歴記録直後に `-wal` ファイルが残ると `index_db_bytes` の見かけ上のサイズが変動するため、cleanup 実行前後で `PRAGMA wal_checkpoint(TRUNCATE)` を実行することで DB ファイルサイズを安定させ、`dry-run` の予定解放量と実削除後の残容量が一致するようにした。
