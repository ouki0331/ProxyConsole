# DEV-040 Automatic request modification rule core

Status: In progress
Owner: implementer
Phase: P5
Product relation: RULE-MATCH-001, RULE-ACTION-001, RULE-AUDIT-001

## 目的

将来到着する HTTP request に対し、local user が定義した条件と action に基づいて query、headers、cookies、JSON、URL-encoded form を転送前に自動変更する persistent rule engine を実装する。変更結果と適用 rule を capture から追跡でき、無効 rule や解析失敗で既存 route を停止させない。

## スコープ

含む:

- persistent rule model/migration
- rule list/get/create/update/delete/copy
- enable/disable、priority、deterministic ordering
- match: route/domain、method、path exact/prefix/regex、query pair、header pair、content type
- action: query/header/cookie の add/set/remove
- action: JSON path set/remove
- action: URL-encoded form pair add/set/remove（duplicate key 対応）
- percent-decoded human-readable value と wire re-encoding
- hop-by-hop header 保護と Content-Length 再計算
- request forwarding 前の rule evaluation/application
- matched/applied/skipped/failed rule IDs と変更 summary の capture/index metadata

- local HTTP API と CLI
- integration test

含まない:

- Web rule management UI（DEV-041）
- response modification
- live interception / manual pause
- multipart file rewrite
- WebSocket frame rewrite
- notification aggregation / browser notification（DEV-042）
- authentication、permission、secret filtering、public deployment hardening（P6）

## 機能ルール

1. rule evaluation は enabled rule を priority、created order、rule ID の安定順序で処理する。
2. disabled rule は保持するが request へ適用しない。
3. preview/dry-run は input または保存済み capture に対する変更候補を返すが、target へ送信しない。
4. query/header/form は list-of-pairs として重複・順序を保持する。
5. decoded value を action input とし、転送時に正しい wire encoding を構築する。
6. `Host`/authority、hop-by-hop header、Content-Length は既存 proxy/replay contract と矛盾しない専用処理を行う。
7. JSON/form action は content type と parse 成功を必要とし、失敗時は request 全体を壊さず rule failure metadata を記録する。
8. 複数 rule が同じ field を変更する場合は安定順序で後続 rule が先行結果を入力として扱う。
9. rule CRUD は稼働中 proxy を再起動せず次 request から反映する。
10. capture detail/search から matched/applied/failed rule と変更 summary を追跡できる。

## 受入条件

1. DEV-001〜DEV-031 の全 test が引き続き成功する。
2. API/CLI で rule CRUD/copy/enable/disable/priority を操作し、restart 後も保持される。
3. route/domain/method/path/query/header/content-type の個別および複合 match が正しい request だけに一致する。
4. query/header/cookie の add/set/remove が duplicate/order semantics を保持して target に到達する。
5. nested JSON path set/remove と duplicate form key add/set/remove が target に期待値として到達する。
6. Unicode、space、reserved character の decoded input が wire 上で正しく encode される。
7. 複数 rule の priority/order と同一 field 競合結果が deterministic である。
8. disabled/non-matching rule は request を変更しない。
9. invalid regex/action/schema は保存時に拒否され、既存 enabled rule と route は継続する。
10. runtime JSON/form parse failure または action failure は fail-open し、元 request が target に到達して failure metadata が残る。
11. dry-run/preview は target/capture を増やさず、適用予定 rule と before/after summary を返す。
12. body/header 変更後に hop-by-hop header が除外され、Content-Length が正しい。
13. modified request capture の detail/search から rule IDs、outcome、change summary を確認できる。
14. WebSocket handshake と未対応 body type は破壊されず、未対応 action は skipped/failed と識別できる。
15. 一つの自動 test command で CRUD、match、actions、ordering、preview、failure、capture metadata を再現できる。

## 実装上の既定

- rule engine は inspector/request forwarding path に統合し、Nginx route generator や browser に business logic を複製しない。
- DEV-030 の ordered pairs、cookie、JSON/form encoding、header normalization helper を可能な限り再利用する。
- regex は Python 標準 engine を既定とし、保存時 compile validation を行う。
- fail-open は機能継続の既定であり、failure を黙って成功扱いにしない。
- rule change metadata は raw request body の完全複製ではなく、field/path と outcome を中心に保存する。
- security hardening を理由に task を停止しない。

## 失敗時の扱い

- non-matching/disabled rule が request を変更する場合は `Blocked` とする。
- runtime failure が request/route を停止する、または元 request を破壊する場合は `Blocked` とする。
- capture から適用 rule/outcome を追跡できない場合は `Ready for review` にしない。
- security hardening を理由に task を停止しない。
